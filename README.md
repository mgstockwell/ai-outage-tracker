# AI Outage Tracker

Curated dataset and dashboard of major consumer outages (banks, payments, carriers, social, cloud, AI) from 2018 to 2026,
built to ask one question: **are outages getting worse now that AI is everywhere?**

**Live dashboard:** https://mgstockwell.github.io/ai-outage-tracker/ (after GitHub Pages is turned on, see below)

## What the data shows so far

<!-- analysis:start -->

_Generated by `scripts/build_data.py` from 56 outages, data through November 16, 2026._

**Not in how often they happen, but in how far they reach.**

- Among outages with a disclosed cause, 70% before ChatGPT's launch and 73% since were a company's own change or software bug: about the same.
- What's new is concentration: 27% of explained outages since the launch came from a shared vendor or provider, up from 0%, so one failure can take down banks, carriers and apps at once.
- The biggest yearly outage since 2023, AWS in 2025 with 17 million reports, is bigger than the biggest before it, Meta (Facebook) in 2021 with 10.6 million. Downdetector's growing audience accounts for part of any rise.
- Uptime Institute's [2026 Annual Outage Analysis](https://intelligence.uptimeinstitute.com/resource/annual-outage-analysis-2026) finds per-site outage frequency has been falling, which this dataset can't measure itself.

## How new outages get in: detect, update, store

Every Monday, `.github/workflows/weekly-scan.yml` runs `scripts/gather_sources.py`, which searches the past 7 days of:

1. **GDELT** news search ([DOC 2.0 API](https://blog.gdeltproject.org/gdelt-doc-2-0-api-debuts/), free, no key)
2. **Google News** RSS search, including a follow-up search for each outage on the watch list
3. **Official status feeds**: Cloudflare, Google Cloud, Azure, AWS, OpenAI, Anthropic
4. **[Updog by Datadog](https://updog.ai)**: measured API degradations (archived; see below)

It keeps items that name a tracked service and an outage word, then:

- **Detect.** A likely new outage (2+ outlets, or on the provider's status page) goes on the **watch list**,
  `data/tracking.csv`, with status `watching`.
- **Update.** Each week, new coverage of a watched outage is added to its row: more outlets, a higher report count,
  how long it lasted, its cause, and a post-mortem link when one appears. Status pages are re-read every week, so a
  post-mortem added to an old incident is picked up. The scan only fills in or raises values; it never blanks one
  you've set.
- **Store.** On its `store_after` date (21 days after the outage by default), the row is copied into
  `data/outages.csv` and marked `stored`. The dataset, JSON, dashboard findings and this README are then rebuilt.

All of it arrives as one pull request a week, *"Outage candidates: week ending …"*. Its description lists what's new,
updated and stored, the full watch list, single-source mentions, and any source that failed. **Nothing reaches the
dashboard until you merge it**, so the pull request is where you check the facts.

### Updog by Datadog archive

The same weekly run also saves [Updog by Datadog](https://updog.ai)'s outage detections into `data/updog/`.
Updog measures API degradations of 30+ SaaS providers and AWS services from real Datadog customer traffic, but only
shows the last ~90 days, so this archive keeps every detection and grows each week. The weekly pull request shows
how many were new and which providers were most degraded. When an outage on the watch list matches an Updog
detection for the same provider and day, its measured start and end time are added, and become its duration if
none is known (`duration_source` = `Updog`). Updog data is Datadog's and isn't covered by this repo's licenses;
see [`data/updog/README.md`](data/updog/README.md).

### Steering the watch list

Edit `data/tracking.csv`, either in the weekly pull request before merging or directly on `main`:

| To… | Do this |
|---|---|
| Store an outage now | set `status` to `store` |
| Drop a false alarm for good | set `status` to `dismissed` |
| Keep collecting updates longer | move `store_after` later |
| Correct a guess | edit `cause_type`, `cause_text`, `duration_hours` or `max_reports`; the scan won't overwrite your values with blanks. To lock a duration you set, put `you` in `duration_source` |
| Track a single-source mention | add a row with `status` `watching` |

How the scan fills fields:

- **Cause** is guessed only when a headline or status update states one ("caused by", "due to", "blamed"…), then sorted
  into the `cause_type` labels by keywords. Otherwise it stays empty and is stored as *Not disclosed*.
- **Duration** comes from phrases like "for nearly 10 hours" or "a 12-hour outage".
- **Reports** is the highest "N reports" figure quoted in coverage, stored as a *Peak (news)* count.

Coverage that arrives after an outage is stored (a regulator report, say) is listed in the pull request under
*New coverage of already-stored incidents* rather than becoming a duplicate; update that row in `outages.csv` by hand.
Change the watch period with `"watch_days"` in `scripts/sources.json`.

The scan does **not** read downdetector.com. Downdetector has no public API and its terms don't allow scraping. Report
counts come from news coverage that quotes Downdetector, and from Ookla's year-end reports.

### Adding or fixing an outage by hand

Edit `data/outages.csv` directly. Allowed values:

- `category`: Banking · Payments & commerce · Cell & ISP · Social & streaming · Cloud & infrastructure · AI services
- `cause_type`: Change / config error · Change / migration · Software bug · Hardware / power · Third-party / vendor · Not disclosed
- `reports_type`: `Total (Downdetector)` for Ookla full-event totals, `Peak (news)` for a peak count quoted in news, or empty
- `era`: `Pre-AI` before 2022-11-30, `AI era` from then on

Then run `python scripts/build_data.py`, which checks every row, rewrites the JSON and refreshes the findings.
If you edit on github.com instead, the *Rebuild analysis* workflow runs it for you after you commit.

Each December or January, add the year's top outage from Ookla's year-end report to `data/yearly_largest.csv`.

### Running it yourself

Python 3.10+ only, no packages to install.

```bash
python scripts/gather_sources.py --dry-run     # print this week's candidates, write nothing
python scripts/gather_sources.py --days 30     # longer lookback, writes data/candidates/
python scripts/build_data.py                   # validate CSVs, rebuild JSON
python -m unittest discover tests              # offline tests
python -m http.server                          # then open http://localhost:8000
```

Edit `scripts/sources.json` to watch more services (add aliases), change search queries, add status feeds or turn
a source off (`"enabled": false`).

## One-time GitHub setup

1. **Settings → Pages**: Source *Deploy from a branch*, branch `main`, folder `/ (root)`.
2. **Settings → Actions → General → Workflow permissions**: choose *Read and write permissions* and tick
   *Allow GitHub Actions to create and approve pull requests* (needed for the weekly PR).
3. **Actions → Weekly outage scan → Run workflow** to test it now instead of waiting for Monday.

## Limits of this data

- **It can't count frequency.** It's a curated list of major, widely reported outages. Recent years are much better
  documented, so more rows in recent years mostly reflects more reporting.
- **Two kinds of report counts.** Ookla's year-end lists give total reports for a whole event; news gives the peak at one
  moment, which is much lower. They're labelled and shouldn't be compared directly.
- **"AI era" is a date, not a cause.** It starts at ChatGPT's launch. Timing alone can't show AI caused anything.
- **Downdetector report counts grow with Downdetector's audience**, not only with outage size.
- Gaming outages (PlayStation, Xbox, Roblox) are left out.

For an exact count of outages over time per platform, you'd need Downdetector's paid history
(Ookla's Downdetector Explorer).
